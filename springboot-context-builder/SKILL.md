# Spring Boot 分层上下文生成器

为单个 Spring Boot 服务生成一套由粗到细的上下文文档，供 AI 编程工具、方案设计和文档撰写参考。

## 核心原则（贯穿全程，务必遵守）

1. **语言：所有生成的上下文文档一律使用简体中文**——标题、表格、正文、说明全部中文；仅代码标识符、类名、路径、注解名保持原样。绝不输出英文文档。
2. **由粗到细**：严格按 L0 → L1 → L2 → L3 → L4 顺序生成，每层为下一层提供背景。
3. **事实与叙述分离**：L3（接口/调用链）、L4（数据模型）是**结构性事实**，必须基于实际代码扫描得到，不能凭印象；L0/L1/L2 的归纳叙述基于扫描出的事实展开。任何不确定的内容标注「待确认」，**绝不编造**。
4. **只读不改**：只读源码，不修改任何业务代码。
5. **持续推进、落盘抗中断**：每完成一个产物立即写盘并更新进度账本，然后自动继续下一步，不要反复停下来征求确认，一路做到全部完成。这样即使中途因回合上限、上下文压缩或网络中断而停止，也能从断点续跑。
6. **一次一个服务**：本 skill 每次只处理一个服务。多服务时让用户逐个仓库运行。

## 扫描通用约束

- 跳过 `src/test`、`target/`、`build/`、`generated-sources/`，以及 `*Test.java`、`*Tests.java`。
- 先用 `find` / `grep` 定位，再读必要文件，不要全量读，控制上下文消耗。
- Spring 依赖注入常按接口类型，追踪依赖时要找到实现类。

## 输出布局

全部产物写入服务根目录下的 `.ai-context/`：

```
.ai-context/
├── _recon.md              # 勘察结果（事实基础）
├── _progress.md           # 进度账本（勾选清单，断点续跑依据）
├── L0-overview.md         # 服务总览（最粗，一页纸）
├── L1-architecture.md     # 架构与工程约定
├── L2-modules/
│   ├── _index.md          # 模块索引
│   └── <模块名>.md         # 每个模块一份
├── L3-api-dependencies.md # 对外 API + 外部调用 + 调用链（事实）
├── L3-api-dependencies.json
└── L4-data-model.md       # 实体/表结构/关系（事实）
```

## 工作流程

开始前先确认当前目录是一个 Spring Boot 服务的仓库根目录。然后按下列步骤推进。**每完成一步就更新 `_progress.md` 并自动进入下一步。**

### 步骤 0 · 勘察（建立事实基础与进度账本）

只勘察不改码。完成：
1. 判断单体还是多模块，列出所有模块及各自根目录（依据 `pom.xml` / `build.gradle`）。
2. 提取服务名（`spring.application.name`，取不到用根 `artifactId`）。
3. 识别构建工具、Java 版本、Spring Boot 版本，以及关键依赖：数据库与 ORM、消息队列、缓存、注册/配置中心、网关、鉴权框架、RPC/HTTP 客户端。
4. 概述顶层包结构和分包方式（按层还是按功能）。

把结果写入 `.ai-context/_recon.md`（事实准确、简洁）。

再创建 `.ai-context/_progress.md`，一份勾选清单，列出全部待办（L0、L1、L2 的每个模块各一项、L3、L4、CLAUDE.md 接入），初始全部 `[ ]`，每完成一项改 `[x]`。

用 3-5 行汇报主要发现，然后继续步骤 1。

### 步骤 1 · L0 服务总览

读 `_recon.md` 作背景，生成 `.ai-context/L0-overview.md`，控制在一页纸内。详细内容规格见 `references/layer-specs.md` 的 L0 小节——开始本步骤前先读该文件。完成后更新进度账本，继续步骤 2。

### 步骤 2 · L1 架构与约定

读 `_recon.md`、`L0-overview.md` 作背景，挑代表性的 Controller / Service / 配置类 / 公共基类阅读（不要全读），生成 `.ai-context/L1-architecture.md`。每条约定尽量给出代码中真实存在的类名/示例作锚点。详细规格见 `references/layer-specs.md` 的 L1 小节。完成后更新账本，继续步骤 3。

### 步骤 3 · L2 模块级上下文（循环，最易中断的一步）

读 `.ai-context/` 下已有的 `_recon.md`、L0、L1。对 `_recon.md` 列出的**每个模块**生成一份 `.ai-context/L2-modules/<模块名>.md`。详细规格见 `references/layer-specs.md` 的 L2 小节。

**关键：一次只处理一个模块，写完一个文件就把账本里对应项改成 `[x]`，然后自动继续下一个模块，不要停下来问是否继续，直到所有模块完成。** 全部完成后生成 `.ai-context/L2-modules/_index.md`（每模块一行：模块名 — 一句话职责 — 相对路径）。继续步骤 4。

### 步骤 4 · L3 接口与依赖链（结构性事实，必须扫码）

这是最关键的事实层，必须基于代码扫描。**开始前先读 `references/dependency-analysis.md`**，按其中的发现 → 提取 API → 提取外部调用出口 → 建立调用链 → 输出 流程执行，生成 `.ai-context/L3-api-dependencies.md` 和 `.ai-context/L3-api-dependencies.json`。完成后更新账本，继续步骤 5。

### 步骤 5 · L4 数据模型（结构性事实）

生成 `.ai-context/L4-data-model.md`。详细规格见 `references/layer-specs.md` 的 L4 小节。以代码与建表/迁移脚本中的真实定义为准，不要据字段名猜含义；推断出来的关系标「推断」。可附 Mermaid ER 图。完成后更新账本，继续步骤 6。

### 步骤 6 · 接入 CLAUDE.md（让上下文自动可用）

Claude Code 每次会话启动会自动加载项目根目录的 `CLAUDE.md`，且它在 `/compact` 后会被重新读回。但文件越长越占上下文、可能降低遵循度（建议单文件别超过约 200 行），所以**不要把五层全文塞进去**。

在项目根 `CLAUDE.md` 追加一个分区（保留已有内容）：
- 一句话说明本服务是什么（取自 L0）。
- 一个「AI 上下文索引」小节，告诉后续会话分层上下文在 `.ai-context/`，并说明何时读哪层：了解整体/做方案设计→L0；写代码要符合风格约定→L1；改某模块→对应 L2（先看 `_index.md`）；涉及接口/调用其他服务/排查调用链→L3；涉及表结构/实体→L4。
- 从 L1 挑 5-8 条最硬性的约定（统一返回、异常、鉴权、命名等）直接内联，作为始终生效的规则。

只放索引和指引 + 少量硬约定，让 L2/L3/L4 按需被读取。更新账本，全部完成后向用户汇报产出清单。

## 断点续跑

如果流程在中途停止（回合上限、上下文压缩、网络中断等），重新触发时：先读 `.ai-context/_progress.md` 和 `.ai-context/` 下已生成的文件，判断哪些已完成、哪些未做或只做了一半，**从第一个 `[ ]` 项继续**，沿用上述全部规则，每完成一项更新账本并自动继续，直到账本全部 `[x]`。若发现某个已存在文件明显不完整或被截断，重做该项。

## 大型项目与多服务

- 单个服务模块特别多时，步骤 3 可分批进行：每次只让其处理几个模块，更稳。
- 多个服务：逐个进入各自仓库根目录分别运行本 skill。如需跨服务的全局依赖图/死接口分析，在所有服务都生成 L3 后单独做汇总（读取各服务的 `L3-api-dependencies.json`）。

## 参考文件

- `references/layer-specs.md` — L0、L1、L2、L4 各层的详细内容规格（生成对应层前阅读）。
- `references/dependency-analysis.md` — L3 接口与依赖链的代码扫描方法（grep 模式清单、API/外部调用提取、注入链追踪、confidence 标注、输出格式、异步/定时/网关等边界情况）。
