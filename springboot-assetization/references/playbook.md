# 老 SpringBoot 项目 AI 资产化 · 策略手册

> 目标不是"用 AI 把老项目改掉",而是**用便宜 token 把老项目变成可理解、可审查、可验证、可继续交给 AI 的资产**。

## 一句话策略

让 agent 多读、多列、多比对、多验证;少让 agent 拍板、少让 agent 猜业务、少让 agent 直接删改。

## 流水线分层(有依赖,不是并发池)

```
Layer 1  抽取/总结        T1 T2 T3       ← 唯一可在所有项目上真并行的一层
Layer 2  关系/图          T4 T5 T6       ← 依赖 Layer 1
Layer 3  风险/候选        T7 T8 T9 T10   ← 依赖 Layer 2
Layer 5  对抗式验证       T12B T12C      ← 等文档生成完,核心任务
P1       可运行性脚手架    T13            ← 标"未验证"
P2       人工主导          T14            ← agent 只提问整理,需要你参与
─────────────────────────────────────────
Layer 4  跨项目分析       T11            ← 多个项目都跑完 Layer1-2 后单独跑
```

编排器(`scripts/assetize.py`)已经把这些依赖写进状态机,`next` 永远只给你"依赖已满足"的任务,不会出现"单项目还没读懂就跨项目分析""文档还没写完就去验证它"。

## 两个 HUMAN GATE(自动流水线唯一会停的地方)

1. **校准 gate(T12C 完成后)** —— 首个项目跑完一条完整闭环后,**你本人**(真懂代码的人)抽查:标了 `[代码已证实]` 的结论是不是真可信?可信度标签是否校准?
   - 校准通过 → `gate-clear after_T12C`,放心铺开到所有项目。
   - 若 `[代码已证实]` 贴在了错误结论上 → 说明 prompt 在量产"自信的垃圾",**停下改 prompt**,再多 token 也救不了。
2. **working-rules 访谈(T14)** —— `09-agent-working-rules.md` 是整个接手包里最值钱的文件,但原料(部落知识、历史事故、线上约束)代码里看不到,必须来自你。让 agent 写它只会一本正经地编。所以 agent 只负责提问 + 整理你的回答。

除了这两处,T1→T13 全自动连跑,不需要你催。

## 为什么对抗式验证(T12)要拆成 B/C 两个角色

用同一份代码让 Agent B 回查 Agent A,二者容易共享盲区,且 LLM 倾向"确认"而非"证伪",会给你一堆橡皮图章式的 `[代码已证实]`。所以:
- **Agent B 的指令是对抗、不对称的**——任务是"挑错/证伪",不是"验证"。金额单位/软删除/状态枚举/时区/幂等这类,不能用一条 grep 或一个测试证明的,一律降级 `[需人工确认]`。
- **Agent C 只整理不分析**——把冲突项和需确认项汇成给人看的队列。

## 跨项目分析(T11,可选)

多个项目各自跑完 Layer 1-2 后,单独发起跨项目分析:重复/分叉的工具类、鉴权与错误码不一致、可抽成 starter/shared-lib 的候选等。这是"公司级工程资产"视角,只给建议不改代码。本 skill 的状态机按单项目组织;跨项目时在每个 repo 都跑完后,把各 `docs/ai/` 一起喂给 agent 即可。

## 与 springboot-dependency-analyzer 的协作

如果环境里装了 `springboot-dependency-analyzer` skill,T4(调用链)和 T9(未使用接口)优先用它——基于注入链/知识图谱的结果比纯 grep 更精确、更省 token。
